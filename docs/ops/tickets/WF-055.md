# WF-055 — Review gate undraft is a no-op

## Outcome

The review gate only logs a draft as ready after GitHub has actually taken it out of draft, and it does not squash-merge in that same pass.

## Notes

Reflect backlog. Do not treat a ruleset bypass as the fix.

- `mark_ready` PATCHes `{"draft": false}` on the pulls API. That endpoint does not take `draft`. The call can succeed as a no-op, the script still prints marked ready, and the PR stays a draft. Use `markPullRequestReadyForReview`, then re-read the pull request and raise if it is still a draft. Another agent may already be switching this call. Do not file a second copy of the same change.
- The event path and the five-minute poll each implement ready-and-merge. A clean merge left the poll skipping drafts. One evaluate function, or one table of cases (green draft, red draft, fork, stale Approve, changes requested, human re-draft) run through both entry points.
- Undraft and merge in one pass means a green draft with an Approve becomes a merge. A human who puts a green PR back in draft gets unmarked on the next poll. Skip undraft when the timeline shows `convert_to_draft` after the PR last left draft. Do not merge in the pass that undrafted. Land this with the real undraft call, or the GraphQL fix turns the gap on.
- Cloud Agent `gh` can 401 while GitHub MCP and git still work. `sessionStart` should say so and point at MCP plus `git merge-tree`. A named pull request is the ticket: do not inject `next_ticket.py` as the only next step.
- A glob rule on `.github/workflows/**` and `ops/scripts/gha_review_gate.py` should load the automation skill. Description matching missed those edits.

## Verify

- [ ] A draft with four green checks leaves draft, and the log is not success if GitHub still says draft.
- [ ] The same run does not squash-merge that pull request.
- [ ] A human `convert_to_draft` after green checks is still a draft after a poll.
- [ ] Both entry points fail the same policy cases in unit tests.
