# Plan: Guest been and want lists on map

## Outcome

On the existing Vite Explore PWA, a **signed-in Guest** reviews private **been** and **want** VisitIntents on a **map or a list**. Done when `/lists` (or one named profile route) is no longer list-only for those two marks, pins reuse Place coords + Leaflet, and PRD-013 is still not shipped. Prove on local compose. Mock-prod follows `main` via stream 1 — do not SSH.

## Out of scope

- Implementing [[ops/tickets/PRD-012]] / [[ops/tickets/PRD-013]] as written (one-tap CHK, 32-county count, category totals, CSV/JSON export, unpublished-place record)
- New VisitIntent marks or a second list API
- Four-kind directory seed/filters ([[ops/tickets/PRD-016]] / [[ops/tickets/PRD-017]]; experiences stay that gap)
- Map rewrite, Mapbox, Next.js, FastAPI
- Public or cross-Guest maps

## Steps

1. Keep the VisitIntent contract from [[ops/tickets/PRD-015]]. Filter published Places by the Guest’s marks (`placesForMark` already exists). Places already have lat/lng.
2. Extend `/lists` with Explore’s `view=map|list` toggle (prefer this over a new app). Map uses existing `MapView`. Default mark `been`; chips for `been` / `want` (and `never` on the list). **Never** on the map is optional, not DoD.
3. Signed-out: prompt to sign in on Explore (`GuestAuth` username/password + GIS already on `main`). Do not invent a second login form.
4. Privacy unchanged: session-only lists; Place pages stay anonymous been count.
5. Vitest for map/list filter helpers. Playwright is cron + MCP ([[ops/tickets/WF-011]]), not automerge.
